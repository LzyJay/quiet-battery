## 迈从耳机充电位解析修正（真机，同日追加）

用户反馈：V9 Pro 2 放进充电座后，本软件显示断开，而 M HUB 显示"⚡ + 2.4G"。当时以为是切到有线模式，实际是**解析错误**。

- 抓帧：充电前 `payload=[0b 01 58]`（0x58=88，正常）。插上充电器后变成 `[0b 01 d8]`（0xD8=216）→ 适配器按"百分比越界"报坏帧 → 一次坏帧即判断开 → 设备被隐藏。两分钟后 `[0b 01 d9]`（0xD9=217），`低7位` 从 88 涨到 89，`0xD8-0x80=0x58`、`0xD9-0x80=0x59`。
- 结论：值字节 **bit7 是充电标志**，低 7 位仍是电量；中间状态字节 `01` 未变，含义仍未知。这也解释了 M HUB 的闪电从哪来。
- 修正：`parse` 先判 bit7 → `(raw & 0x7F, PowerState::Charging)`；未置位时保持原语义（值即电量，充电状态未知）。超范围仍然报坏帧，不放宽完整性检查。
- 测试：新增充电位用例（0xD8→88/Charging、0xD9→89/Charging、0x80–0xE4 全区间低7位映射、以及原有校验和/长度/外来命令边界）。
- 真机：`--scan` 读到 V9 Pro 2 **98% / Charging**（充电中持续上升 88→89→92→97→98），窗口显示"2.4G · 充电中 · 刚刚更新"并带闪电，不再是断开。
- 顺带修正 JSON：`power_state` 原先只在 `metadata_known=true` 时才输出，导致这类"只报百分比 + 充电位"的设备在 `--scan`/`--status` 里看不到状态。现在只要是**观察到的状态**（非 Unknown）就输出；未观察仍为 null，不编造。
- 事故记录：本次与其他会话在同一工作区并行操作，`git add -A` 把适配器修正一起卷进了 `7cf5553`（提交说明只提到使用时长）。代码与测试都在，只是提交说明不完整。另一次"托盘注册不上"经复现是实例争用（同时存在多个进程），干净启动后 `tray_registered=true`，与代码无关。
- 顺带发现并修正：进程重启时把缓存值当成"断开后重连"，只要电量比上次保存的高就重置使用时长。现在只认**已确认的断开→重连**（`connection_known && !connected`），启动时的首次样本不算重连。
### 追加：拔线后没有重置使用时长

用户拔掉充电线后，界面显示"已使用9分钟"。查状态：`power_state` 为 null（即 `Unknown(255)`），`usage_since` 仍是 10 分钟前。

- 根因：耳机适配器在 bit7 清零时返回 `Unknown(255)`，而"离开充电器"的判定要求新状态是 `Discharging`/`Full`，所以跳变不成立、不重置。同厂的鼠标适配器对充电字节 `0` 恰恰返回 `Discharging`，两边不一致。
- 修正：bit7 是布尔量，清零即"未在充电"，返回 `Discharging`。这也和"只报百分比"的设备的默认语义一致；不写清楚就永远等不到重置。
- 真机：改后 `--scan` 读到 V9 Pro 2 `98% Discharging`（未充电）、A5 `62% Charging`（在充电座上），证明两种状态都能正确区分。
- 注意：本次修正**不会追溯**已经错过的这次跳变——该设备的使用起点要等下一次"充电→拔线"才会归零。这属于无法凭现有数据推断的部分，不做事后猜测。

## 去掉行内手动刷新、2.4G 静默断开（真机，同日追加）

2026-10-27，用户反馈"蓝牙耳机正常，但两个2.4G设备断开既不提示也不消失"后修正。

- 根因不在提示逻辑，在连接判定：接收器还插着时适配器照样枚举出 vendor 集合，只是查询无回复，Manager 原先把"可恢复占位候选"一律当已连接，于是 2.4G 设备永远不消失，也就永远没有状态变化可提示。现场证据：`mchose-hs`（V9 Pro 2 接收器）读到 88% 后 17 分钟无更新，仍以 connected=true 留在列表。
- 新规则：枚举成功但查询无回复时，**连续两个发现周期**按断开处理并隐藏，缓存、选择与托盘偏好保留；任意一次成功回复立即恢复并清零。经典蓝牙仍以 `fConnected` 为确认信号，一周期即断开，不套用超时规则。单次超时不会被当成断开。
- 真机验证（同一台机器、同一批设备）：旧成品 17 分钟后该行仍在；新成品在第二个发现周期后该行消失，`--status` 中该设备 connected 由 true 变 false，`notification.submissions` 由 0 变 1，`shown=1/timed_out=1`，即"设备已断开"弹窗真实弹出并被系统收起。窗口截图确认列表只剩 A5 V3 Ultra 一行。
- 界面：主页面行内"手动刷新"按钮移除，手动刷新只保留在托盘右键菜单。腾出的宽度给型号列（140→232），电池与百分比右移，`MCHOSE A5 V3 Ultra` 可完整显示，更长仍按省略号截断、悬停看全名。蓝牙耳机行因此不再需要滚动查找按钮。
- 顺带修正：查询失败时不再把连接方式重置为未知——链路类型是适配器证据，与本次查询成败无关；失败设备现在仍显示"2.4G"。
- 测试：更新 `darmoshark` 里原先断言"一次静默仍算已连接"的用例（改名 `silent_receiver_keeps_the_value_then_hides_without_losing_health`），改为一次保留、二次隐藏、回复后恢复；新增 Manager 的"静默两周期隐藏并双向提示"和"一次回复清零计数"两项。146 通过、3 项既有环境失败。
- 未验证：重新开机后的"已连接"弹窗（本轮只观察到断开方向）、静默期间正在充电的设备、连续快速开关造成的抖动。

### 追加：判定太慢导致的"仍然不消失"（同日）

- 关掉鼠标时接收器回的是**校验和不匹配的帧**（连续三次 `--scan` 一致），不是超时。这是"接收器背后没有有效设备"的明确信号，不该等第二轮。

## v0.5.0：私有通道资料核对（仅资料，无代码改动）

2026-10-27，本轮不新增适配器、不改程序。目的是确定"电量不在标准通道时还有哪些路可走"，并判断迈从 V9 Pro 2 的 2.4G 模式是否值得继续投入。结论整理为[私有通道资料](RESEARCH-PRIVATE-CHANNELS.md)与[调查踩坑记录](PITFALLS.md)。

- 通道可达性（资料推断加本机结构核对）：USB 复合设备的三条接口由不同类驱动接管。HID 集合走 `hidusb.sys`，用户态 `ReadFile`/`hidapi` 可直接只读访问；UAC 音频接口走 `usbaudio.sys`，被类驱动独占，用户态无入口，只能以 WinUSB 替换驱动，代价是设备同时失去录音放音；厂商驱动的 KS 节点可经 `IKsControl::KsProperty` 访问（`IConnector::GetDeviceIdConnectedTo` → `IMMDeviceEnumerator::GetDevice` → `IMMDevice::Activate(IID_IKsControl)` → `IPart::GetLocalId` → `KsProperty`），但属性集必须由驱动实现，通用 `usbaudio.sys` 不提供电池属性。
- 据此把"音频接口私有通道"从候选里排除：协议层可能成立，操作系统层没有用户态入口。这不是权限问题，是接口所有权问题，本项目"只查询、不换驱动、不依赖厂商软件"的约束下无解。
- 核对标准通道：HID Generic Device Controls `0006:0020` Battery Strength 是随包接收器场景的规范手段，社区文档明确推荐，并警告不要放进系统独占的顶层集合（鼠标/键盘/笔/触摸屏为独占，Consumer Controls 与 HID UPS Battery 为共享）。本机 `3837:6011` 接收器的集合为 `FF07:0222`、`000C:0001`、`000B:0005`、`000C:0001`，实测无 `0006:0020`，该通道不存在。
- 核对 V9 Pro 2 的其余候选，全部排除，均留证据：厂商集合 `FF07:0222` 无电量字段（实测）；BES HID 通道 `0x0b` 字节连续三次采样为 `0x58`→`0xD9`→`0xDA`，是自增计数器而非百分比（实测）；Windows HFP 属性可用但只是最后一次上报的缓存值（实测）。剩余唯一有信息增量的动作是抓取厂商软件查询电量时的真实 HID 流量，本机 USBPcap 过滤器尚未绑定根集线器实例，需重启后生效。
- 参考实现核对（资料推断，未在本机复现）：`2.4G-battery-viewer` 的多策略降级与协议描述表、Razer BlackShark WebHID 的序号关联与接口隔离、HeadsetControl 的设备注册表与能力位掩码、HyperXWM 的单 report ID 多功能字节复用。可借鉴点与常见问题已按主题归入上述两份文档。
- 本轮没有真机读数变化，不涉及构建、测试或资源采样，不产生新 EXE，因此不给哈希，也不改动 README 支持表中已记录的数字。
