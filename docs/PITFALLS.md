# 调查踩坑记录

记录已经发生过、并且会重复发生的判断错误。每条写清症状、根因和正确做法，供后续调查直接规避。

与[私有通道资料](RESEARCH-PRIVATE-CHANNELS.md)的分工：那份讲外部世界的机制，这份讲我们自己怎么判断错的。

## 1. 用关键词过滤属性，漏掉裸 GUID 键名

**症状**：断言"Windows 没有暴露经典蓝牙耳机的电量"，据此把 5 个耳机全部列为不支持。

**根因**：筛选 PnP 设备属性时按 `Battery|Power` 匹配键名。而 HFP 电池属性的键名是裸 GUID 加序号——`{104EA319-6EE2-4701-BD47-8DDBF425BBE5} 2`——里面没有任何可读单词。过滤先于观察，等于用假设裁掉了答案。

**正确做法**：先无过滤导出全部属性，再决定筛什么。**"我的检索没命中"不等于"系统没有这个字段"**。未知键名只能记为未知，不能记为不存在。

**代价**：结论整个反了。同一批设备正确实现后，5 个耳机全部读到真实电量，且与 Windows 设置界面逐一吻合。

## 2. 把 report ID 当成报文头

**症状**：迈从 V9 的帧按 `55 AA` 当双字节报文头解析，长度字段永远错位，扫遍参数表也找不到电量。

**根因**：Windows HID 的 Input Report 首字节是 **report ID**，属于传输层，不属于报文语义。`hidapi` 与原生 `ReadFile` 对首字节的处理还不一致：前者通常剥离，后者按集合类型决定是否包含。把两者混为一谈，协议就从第一个字节开始歪。

**正确做法**：先单独确认 report ID 槽位是否存在、由谁消耗，**再从下一字节开始解释协议**。正确布局是 `report id 0x55 | AA | version | flags | len LE | cmd | payload | XOR`，其中 `0x55` 是 report ID，`0xAA` 才是报文起点。

**旁证**：厂商软件界面同时显示"Report 0x55 / 命令 0x65"，这一条直接印证了分层。

## 3. 完整性校验放在语义过滤之后

**症状**：`mchose.rs` 的损坏帧测试失败——期望 `Err`，实际返回 `Ok(None)`，损坏的帧被当成"无关报文"静默跳过。

**根因**：解析顺序是"先比命令号，不匹配就跳过"，校验和检查排在后面。当单字节损坏正好落在命令号字段上时，永远走不到校验那一步。

**正确做法**：**完整性校验先于语义过滤**。校验和不过的帧是"坏帧"，应报错；命令号不匹配的帧才是"别人的帧"，应忽略。两者不能合并成同一个分支。

**推广**：任何"先分类再验真"的解析器都有这个漏洞。顺序应当是 长度 → 校验 → 身份 → 语义。

## 4. 过早给出"不支持"

**症状**：第一轮就下了"耳机读不到电量"的结论，被用户用第三方工具截图直接推翻——同一个型号，别人能显示百分比。

**根因**：把"我试过的路径都没通"当成了"设备不具备该能力"。这两件事在证据等级上差得很远。

**正确做法**：结论分三档写——**已排除**（穷举过该通道并留下记录）、**未找到**（试过但没穷尽）、**不支持**（只有前两者都完成才允许）。"别人做得到"是强信号，说明通道存在，只是还没找到。

**代价**：一轮完整的返工。

## 5. 抓包工具装了不等于生效

**症状**：USBPcap 连续 4 次抓包结果都是 0 bytes，日志只有 `Couldn't open device - 2`。

**根因**：过滤器已经写进注册表 `UpperFilters = hrdevmon, USBPcap`，但**没有绑定到根集线器实例**，需要重启才完成绑定。注册表里有条目 ≠ 驱动已挂载。

**正确做法**：抓包前先确认设备管理器里能看到 `USBPcap1` 一类的接口实例，看不到就不要开始。另外停止抓包不能用 `taskkill`——会丢缓冲区，应该发 `CTRL_BREAK_EVENT` 让工具自己收尾。

**推广**：任何"注册表已配置"的结论都要再验一次实际挂载状态。

## 6. 把"协议上走音频"当成"用户态能读音频"

**症状**：得知"电量经蓝牙传输、数据经 2.4G"后，倾向于去查音频接口。

**根因**：混淆了协议层的事实和操作系统层的事实。USB 复合设备的不同接口由不同类驱动接管：HID 走 `hidusb.sys`，音频走 `usbaudio.sys`。前者用户态可直接 `ReadFile`，后者被类驱动独占，用户态没有入口。

**正确做法**：判断可达性时先问"这个接口归哪个类驱动"，再问"协议怎么解析"。顺序反了会白做。

**结论**：音频接口这条路在本项目约束下（不换驱动、不破坏设备原功能）基本可以关掉。详见[私有通道资料](RESEARCH-PRIVATE-CHANNELS.md)。

## 7. 把超时当成协议错误

**症状**：接收器在耳机未开机时完全不回任何数据，与"命令不被支持"表现相同。

**根因**：两者都表现为"等不到回复"。

**正确做法**：用**超时**与**拒绝**区分——超时是链路没通（设备休眠/未连接），错误码是命令不认。前者应提示"确认设备已开机"，后者才应判为协议不匹配。收不到回复时不要判失败，也不要返回 0%。

## 8. 结论写在文档里，但没写"为什么排除"

**症状**：只留"XX 未支持"，后来的调查者会把已经排除的通道再走一遍。

**根因**：记录结论不记录排除依据。

**正确做法**：每次排除都写清**通道名 + 排除了什么 + 用什么证据**。V9 Pro 2 的现有记录就是按这个格式写的：标准 `0006:0020` 不存在（实测）、`FF07:0222` 无字段（实测）、BES `0x0b` 是自增计数器（三次采样）。这三条写明后，后来者不必重试。
